# AI Clinical Case-Taking Platform — Current MVP Project Requirement

## 1. Project Overview

Build a web-based **AI-powered multilingual clinical case-taking and patient intake platform** for the SIH prototype.

The system will simulate a hospital kiosk using a **laptop/desktop browser**. The laptop's built-in webcam will be used for patient face enrollment and face verification.

For the current MVP, **mobile number will be used instead of RFID** for patient identification. The system must be architected so that the mobile-number identification layer can later be replaced by an RFID reader without changing the core patient/session/authentication architecture.

The system is **not an AI doctor**. It must not independently diagnose diseases, prescribe medication, or override a doctor. AI assists with information collection, document extraction, organization, and summarization. The doctor remains the final clinical decision-maker.

# 13. AI Clinical Assistant

The AI assistant conducts the patient interview.

It must:

- Speak questions
- Accept patient answers
- Ask relevant follow-up questions
- Confirm important information
- Adapt questions according to previous answers
- Maintain clinical context

It must not:

- Claim to be a doctor
- Diagnose
- Prescribe medicine
- Change medication
- Override doctor decisions

Example:

```text
Patient:
"I have stomach pain."

AI:
"When did the pain start?"

Patient:
"Three days ago."

AI:
"Where exactly do you feel the pain?"

AI:
"Does anything make it better or worse?"

```

```http

```

Input should contain the relevant session context.

The LLM should return structured output.

Example:

```json

  "required": true,
  "reason": "onset"

```

The exact clinical questioning logic must be configurable and validated rather than allowing the LLM to freely invent an unlimited questionnaire.

## 8. PatientIdentifier

This abstraction allows the current mobile-number identification to be replaced by RFID later.

```text
id                  UUID PK
patient_id          UUID FK
identifier_type     VARCHAR NOT NULL
identifier_value    VARCHAR NOT NULL
is_primary          BOOLEAN DEFAULT FALSE
is_active           BOOLEAN DEFAULT TRUE
created_at          TIMESTAMP
updated_at          TIMESTAMP
```

Allowed current/future identifier types:

```text
MOBILE
RFID
```

Current:

```text
MOBILE → +919876543210
```

Future:

```text
RFID → A73F912C
```

Add a uniqueness constraint on the active `(identifier_type, identifier_value)` pair.

# 36C. Important Data Design Rules

1. PostgreSQL is the source of truth for structured application data.
2. Cloudinary stores document/media binaries; PostgreSQL stores their metadata and references.
3. Qdrant stores embeddings/chunks for semantic retrieval and is not the primary database.
4. `PatientIdentifier` isolates mobile/RFID identity mechanisms.
5. `FaceEnrollment` isolates biometric verification from the patient profile.
6. `Answer` stores clinically meaningful structured answers; do not use it as a generic chat-message table.
7. `Case.summary` should be structured JSONB plus optional human-readable `summary_text`.
8. Patient corrections and doctor corrections must be auditable through `CaseEdit`.
9. Doctor-verified data must not be silently overwritten by AI.
10. All timestamps should be stored in UTC and converted for display at the frontend.
11. Use soft deletion/status fields where medical records must remain auditable.
12. Do not store raw face frames or unnecessary biometric images.
13. Never store medical history inside RFID data.
14. Do not put Cloudinary, LLM, Qdrant, STT, or TTS secrets in the frontend.
15. Backend services must enforce patient/session ownership and role authorization.

# 49. Core Product Statement

Build a **multilingual, accessible AI-assisted clinical intake platform** that identifies patients using a mobile-number-based MVP identity flow, verifies them using the laptop webcam, collects adaptive clinical history through voice/text interaction, captures vitals and previous medical documents, stores documents securely using Cloudinary, extracts medical information using OCR/AI, creates a longitudinal timeline, allows the patient to review and correct the captured information, generates a structured case summary, and routes the case to the appropriate consultant for final doctor verification.

The system must be modular and hardware-ready so that the current mobile-number identification mechanism can later be replaced by RFID without redesigning the core backend.
